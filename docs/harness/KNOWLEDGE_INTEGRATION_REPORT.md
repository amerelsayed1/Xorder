## 3. Knowledge retrieval workflow
Defined in `references/knowledge-retrieval.md`, invoked as `/project-documentation context <feature or query> <plan|implement|test|bug|review>`:
1. `grep -n -i` the inventory; open only the matching feature block (never the whole inventory or all docs).
2. Open only the sections the phase needs (a table maps phase → sections).
3. Freshness: `git -C <repo> diff --name-only <recorded sha>..HEAD -- <evidence files>` plus `git status --short -- <evidence files>` per repo. Verdict `fresh`, `needs verification`, `stale` or `missing`.
4. Spot-check the two to five load-bearing claims in source.
5. Writers repair narrowly (`feature <slug>` / `update <slug>`); read-only callers report the gap and proceed on verified source. Missing docs never block work.
Maintenance (`progress-management.md`): the progress file records the source revisions each feature was documented against; `update` maps `git diff` files to features through the inventory's evidence lists, marks them `stale`, refreshes only those, records unmapped changes as *uncovered*, and resumes from the progress file. No full scan runs on code edits (SKILL.md rule 9).

## 5. Findings about the product surfaced by the documentation work (reported, not changed)
Evidence is in `docs/features/pos-shifts/FEATURE.md` (Security considerations, Known limitations). For the owner to decide:
1. Cloud `open` accepts any branch of the tenant, not the terminal's branch; the terminal can then neither close nor report that shift (`PosShiftService.php:49-53,303`).
2. A replay of an already closed shift returns before the capability check (`PosShiftService.php:99-107`), and the idempotency hashes ignore `variance_reason`, `denominations`, `branch_id`, `occurred_at` (BR-9).
3. `acting_user_id = null` skips every capability check on shifts, movements and orders (v1 relaxation).
4. The handover approval is recorded only in the POS local audit, not on `pos_shifts` and not sent to the cloud.
5. `GET /api/pos/shifts/current` and `/report` apply no capability, unlike the contract text, and no client calls them.
6. Cloud expected cash can differ from the till's because payments are attributed to a shift only if the order named an open shift when it arrived (BR-12).
7. Wrong or stale statements in the nested repos' prose: `apps/xorder-cloud/CLAUDE.md` mentions `Policies/`; the cloud `POS_TO_BACKEND.md` POS-BE-009 section says "implementation not started" while the index says READY.

## 6. Missing capabilities and limits
- **Coverage:** the inventory is a seed (64 features, 63 `pending`, footprint `UNVERIFIED`); uncovered source is not computed; only one feature was traced end to end. Retrieval for any other feature returns a row with entry-point hints and `missing` freshness until it is documented.
- **No automation:** freshness checks and `update` run when a skill or the user invokes them. There is no hook or CI step that flags stale features after commits. A small script implementing the freshness check would make this cheap and consistent (recommended below).
- **Enforcement is instructional:** skills and agents are told to call `context`; nothing stops a session from skipping it. The testing agent skipped one step in the dry run for that reason.
- **Subagents cannot invoke skills**, so they read the inventory and docs directly following `.claude/rules/knowledge.md`; the main session runs `context`.
- **Context cost:** the implementation agent read FEATURE, TECHNICAL, API and DATABASE in full (FEATURE.md alone is about 140 lines) although the phase table asks for sections only; documents are not machine-sectioned. Feature docs should stay short and the brief format should be produced by the main session.
- **Validation depth:** one independent pass, by one reviewer, on one feature; PostgreSQL and concurrency behavior cannot be validated by reading and remain UNVERIFIED.
- **Not integrated:** repo-level symlinked agents/skills (see section 2); nested repo `CLAUDE.md` files.
- **Tests:** none were run for this work except as already recorded in `docs/testing/reports/`; `pos-shifts` has no feature-targeted run (`TEST_REPORT.md` says so).
