# Xorder — مرجع تصميم المنتج لـ ChatGPT

> **الغرض من الملف:** هذا المستند هو الـ source of truth الذي يُرفق مع أي طلب تصميم UI/UX بالذكاء الاصطناعي. يشرح المنتج، المستخدمين، الخدمات، الشاشات، تدفقات الاستخدام، الهوية الحالية، والقيود التقنية حتى تكون المقترحات قابلة للتنفيذ ومتسقة.
>
> **آخر مراجعة:** 29 يوليو 2026 — مبني على الحالة الفعلية للكود، وليس تصورًا مستقبليًا.

## 1. ملخص المنتج

**Xorder** منصة SaaS متعددة العملاء (Multi-tenant) للمطاعم والكافيهات. تمنح كل مطعم منيو رقميًا عبر QR، وتسمح — حسب الباقة — باستقبال الطلبات عبر WhatsApp أو داخل النظام، وإدارة الفروع والطاولات والعملاء والتقييمات والتقارير.

المنتج يتكون من أربع تجارب مترابطة:

1. **الموقع التسويقي:** تعريف Xorder، عرض المزايا والباقات، تجربة منيو Demo، واستقبال طلبات التواصل.
2. **لوحة Super Admin:** إدارة المطاعم، الباقات والاشتراكات، العملاء المحتملين، محتوى الموقع، والتحليلات العامة.
3. **لوحة إدارة المطعم:** إدارة المنيو والطلبات والفروع والطاولات والعملاء والتقييمات والتقارير.
4. **منيو العميل:** تجربة Mobile-first لمسح QR، تصفح الأصناف، تكوين الطلب، وإرساله إلى WhatsApp أو نظام المطعم.

### القيمة الأساسية

- استبدال المنيو الورقي بمنيو QR سهل التحديث.
- استقبال الطلبات بدون إجبار العميل على تنزيل تطبيق أو إنشاء حساب.
- دعم العربي والإنجليزي وواجهات RTL/LTR.
- تخصيص منيو كل مطعم بلونه وشعاره وصوره.
- توحيد إدارة الطلبات وخدمة الطاولات وبيانات العملاء.
- توفير بيانات تساعد المطعم على فهم المبيعات والأصناف والأماكن.

### السوق والسياق

- السوق الأساسي الحالي: مصر، والأسعار الافتراضية بالجنيه المصري EGP.
- الجمهور: مطاعم، كافيهات، مخابز وحلويات، وعربات طعام، مع قابلية التوسع لأنشطة ضيافة مشابهة.
- أسلوب الكتابة المطلوب: واضح، عملي، ودود، وغير تقني. تجنب الوعود المبالغ فيها.

## 2. أنواع المستخدمين

### أ. زائر الموقع التسويقي

يريد أن يفهم المنتج بسرعة، يرى كيف سيبدو المنيو، يقارن الباقات، ثم يطلب Demo أو يتواصل عبر WhatsApp.

### ب. Super Admin / فريق Xorder

يدير المنصة كلها: إضافة المطاعم وحساباتها، تخصيص الباقات والاشتراكات، متابعة مؤشرات النشاط والعملاء المحتملين، وتعديل محتوى الموقع التسويقي.

### ج. Restaurant Admin / مدير المطعم

يدير مطعمًا واحدًا فقط. احتياجاته اليومية هي متابعة الطلبات، تحديث توافر الأصناف، إدارة المنيو، وطباعة QR. وتظهر له الوظائف المتقدمة فقط إذا كانت ضمن باقته.

### د. Diner / عميل المطعم

يفتح المنيو من QR أو رابط، غالبًا من هاتفه وفي بيئة سريعة ومزدحمة. لا يسجل الدخول. يريد الوصول للصنف والسعر وإتمام الطلب بأقل خطوات ممكنة.

## 3. الخدمات والخصائص

### المنيو الرقمي

- رابط وQR خاصان بكل مطعم، وQR مستقل لكل طاولة عند تفعيل إدارة الطاولات.
- أقسام وأصناف مرتبة، صور، وصف، سعر، خصم، حالة التوفر، وتمييز الأصناف المقترحة.
- أصناف لها مجموعات اختيارات وإضافات، وحد أدنى/أقصى للاختيار.
- Combos ووجبات مجمعة لها مجموعاتها واختياراتها.
- بحث داخل المنيو وتبويبات أقسام Sticky.
- عربي وإنجليزي مع RTL/LTR، ويمكن للمطعم تعطيل ثنائية اللغة.
- تخصيص اللون الرئيسي والشعار وصورة الغلاف وبيانات المطعم وروابطه الاجتماعية.

### الطلبات

- أنواع الطلب: داخل المطعم `dine_in`، استلام `pickup`، وتوصيل `delivery` حسب الباقة والفرع.
- أوضاع التشغيل:
  - `whatsapp`: السلة تتحول إلى رسالة WhatsApp فقط.
  - `system`: الطلب يُسجل في النظام فقط.
  - `both`: يُسجل في النظام ويُفتح WhatsApp أيضًا.
- العميل يضيف الاسم والهاتف، والعنوان للتوصيل، والبريد اختياريًا، وملاحظة عامة أو ملاحظات على الأصناف.
- تأكيد نجاح الطلب مع كود الطلب عند التسجيل داخل النظام.
- لوحة طلبات، Live Board، إشعارات وعدادات للحالات الجديدة.

### الفروع والطاولات

- مطعم واحد قد يملك عدة فروع حسب الباقة.
- كل فرع يحدد بيانات التواصل وأنواع الطلب المتاحة.
- مناطق جلوس Dining Areas داخل الفروع.
- طاولات مرتبطة بمنطقة وفرع، ولكل طاولة QR Session يحدد طلب `dine_in` تلقائيًا.
- العميل على الطاولة يستطيع طلب الفاتورة عند تفعيل `bill_requests`.

### العملاء والتقييمات

- سجل عملاء وتفاصيل العميل وتاريخ طلباته عند تفعيل `customer_tracking`.
- تقييم خاص بعد الطلب عند تفعيل `internal_reviews`.
- شاشة إدارة التقييمات، ملاحظات داخلية، ومؤشرات للتقييمات السلبية.

### التحليلات والتقارير

- Dashboard بأهم الأرقام والاتجاهات.
- Insights للطلبات والمبيعات والأداء.
- تقرير أداء المنتجات والفترات الزمنية.
- مقارنة مناطق الجلوس: الطلبات، طلبات الفاتورة، متوسط التقييم، والتقييمات السلبية.

### الباقات والاشتراكات

الباقات ديناميكية ويمكن للـSuper Admin تعديلها. القيم الابتدائية الحالية:

| الباقة | السعر الابتدائي | الوظائف الأساسية |
|---|---:|---|
| Menu Starter | مجانية | منيو QR فقط بدون طلبات |
| Menu Plus | 749 EGP | منيو QR + طلب WhatsApp + استلام وتوصيل |
| Restaurant Pro | سعر مخصص | الطلب داخل النظام وWhatsApp، العملاء، الطاولات، الفاتورة، التقييمات، التحليلات، والفروع المتعددة |

اشتراك المطعم قد يكون `TRIAL` أو `ACTIVE` أو `EXPIRED` أو `SUSPENDED`. حالة المطعم نفسه قد تكون `ACTIVE` أو `SUSPENDED` أو `ARCHIVED`.

## 5. أهم تدفقات الاستخدام

### طلب عميل من رابط عام

`فتح المنيو → اختيار اللغة/الفرع عند الحاجة → بحث أو تصفح قسم → فتح الصنف → اختيار الإضافات → إضافة للسلة → اختيار استلام أو توصيل → إدخال البيانات → تأكيد → تسجيل الطلب و/أو فتح WhatsApp → نجاح → تقييم اختياري`

### طلب عميل من QR طاولة

`مسح QR → ربط الجلسة بالطاولة والفرع والمنطقة → تصفح المنيو → الطلب يصبح dine_in فقط → إرسال الطلب → متابعة النجاح → إمكانية طلب الفاتورة`

### تشغيل المطعم اليومي

`دخول المدير → مراجعة Live Board والإشعارات → قبول/تحديث الطلبات أو طلبات الفاتورة → تعديل توافر الأصناف سريعًا → مراجعة مؤشرات اليوم`

### إعداد مطعم جديد

`Super Admin يختار الباقة → يُدخل هوية المطعم وبيانات المدير → يراجع الخصائص الناتجة من الباقة → يضيف أول فرع → يراجع وينشئ الحساب → مدير المطعم يكمل الملف والمنيو → ينزل QR`

## 7. اتجاه التصميم والهوية الحالية

### شخصية العلامة

Xorder يجب أن يبدو **حديثًا، دافئًا، موثوقًا وسهلًا**. المنتج يخدم الأكل والضيافة، لذلك لا نريد شكل SaaS باردًا أو Corporate مبالغًا فيه. في الوقت نفسه يجب ألا يصبح طفوليًا أو مزدحمًا.

### الخطوط

- الخط الأساسي الحالي: **Tajawal** للعربي والإنجليزي.
- البيانات التقنية والروابط يمكن أن تستخدم **IBM Plex Mono**.
- يجب اختبار العناوين والأزرار والجداول بالعربي الفعلي، وليس Lorem Ipsum فقط.

### ثيم لوحة المطعم — Warm

- Page: `#F8F5EF`
- Surface: `#FFFFFF`

- Sidebar: `#1C1712`
- Borders: `#ECE5D9`
- الطابع: دافئ، مرتبط بالضيافة، وخفيف على الاستخدام اليومي.

### ثيم Super Admin — Indigo

- Accent: `#3D4A7A`

- الطابع: تشغيلي، واضح، وأكثر حيادًا من لوحة المطعم.

- خلفية Cream: `#FFF8EA`

- Tables للبيانات الكثيفة، وCards للأرقام والملخصات.

- تجنب Glassmorphism، neon، الظلال الثقيلة، والـrounded pills في كل عنصر.

## 8. قواعد UX غير قابلة للتفاوض

- **Mobile-first لمنيو العميل**، ثم Tablet وDesktop. لوحات الإدارة Desktop-first لكنها يجب أن تعمل على Mobile.
- دعم كامل لـRTL وLTR باستخدام logical properties؛ لا تعكس الأيقونات التي لها معنى ثابت بلا داعٍ.
- لا يوجد تسجيل دخول لعميل المطعم، ولا شاشة إنشاء حساب أثناء الطلب.
- السعر والتوفر وCTA للإضافة يجب أن تكون واضحة من بطاقة الصنف.
- الصنف ذو الاختيارات لا يُضاف مباشرة؛ يجب فتح شاشة الاختيارات أولًا.
- من QR الطاولة يكون `dine_in` هو النوع الوحيد ولا يُطلب من العميل اختيار طاولة يدويًا.
- من الرابط العام لا يظهر `dine_in` لأنه لا توجد طاولة يمكن توجيه الطلب إليها.
- التوصيل يحتاج عنوانًا، أما الاستلام وداخل المطعم فلا يحتاجانه.
- وضع WhatsApp يحتاج رقم WhatsApp؛ وضع System-only لا يحتاجه.
- العمليات الخطرة مثل الحذف أو تعليق مطعم تحتاج Confirmation واضحًا.
- كل شاشة بيانات يجب أن تتضمن Loading، Empty، Error، Success feedback، وحالة صلاحية/Read-only عند الحاجة.
- لا تكشف بيانات مطعم داخل مطعم آخر، ولا تضع اختيار Restaurant ID في نماذج مدير المطعم.
- اللون المخصص قد يكون فاتحًا أو غامقًا؛ حافظ دائمًا على contrast مقروء.
- استخدم نصوصًا عربية واقعية وأرقامًا وأسعارًا طويلة لاختبار الالتفاف.
- استهدف WCAG 2.2 AA: contrast، focus واضح، keyboard navigation، labels، وtouch targets لا تقل عن 44px في تجربة العميل.

## 9. مقاسات وحالات مطلوبة في أي تسليم تصميم

عند طلب تصميم شاشة، قدّم على الأقل:

- Mobile بعرض 390px لمنيو العميل.
- Tablet بعرض 768px عند تأثير التخطيط.
- Desktop بعرض 1440px للوحة الإدارة أو Landing.
- RTL عربي وLTR إنجليزي إذا تغيّر التخطيط جوهريًا.
- Default، Loading، Empty، Error، Disabled/Unavailable، وSuccess حسب طبيعة الشاشة.
- وصف التفاعل: hover، focus، open/close، validation، confirmation، responsive behavior.
- قائمة المكونات القابلة لإعادة الاستخدام والـtokens الجديدة إن وجدت.

## 10. ما لا يجب اختراعه بدون طلب

- تطبيق Mobile Native؛ المنتج الحالي Web/PWA.
- دفع إلكتروني داخل المنتج.
- حساب أو Loyalty wallet لعميل المطعم.
- تتبع توصيل على الخريطة أو تطبيق للكابتن.
- حجز طاولات مسبق.
- Marketplace يجمع المطاعم.
- Kitchen Display System مستقل؛ الموجود حاليًا Live Board داخل لوحة المطعم.
- خصائص غير موجودة لمجرد ملء الشاشة. إذا كان هناك اقتراح جديد، افصله بوضوح تحت عنوان **Future concept**.

## 11. قالب Prompt جاهز للاستخدام مع ChatGPT

انسخ النص التالي، أرفق هذا الملف، ثم املأ ما بين الأقواس:

```text
أنت Senior Product Designer متخصص في SaaS ومنتجات المطاعم ثنائية اللغة.
اعتبر ملف AI_DESIGN_BRIEF_AR.md المرفق هو المصدر الأساسي لفهم Xorder، ولا تخترع خصائص تخالفه.

المطلوب: تصميم [اسم الشاشة أو الـflow].
المستخدم الأساسي: [Diner / Restaurant Admin / Super Admin / Landing visitor].
الهدف: [النتيجة التي يجب أن يصل إليها المستخدم].
المنصة والمقاس: [Mobile 390 / Tablet 768 / Desktop 1440].
اللغة الأساسية: [Arabic RTL / English LTR / Both].
```

## 12. Checklist قبل اعتماد أي Design

- هل الشاشة تخدم مستخدمًا وهدفًا واضحين؟
- هل الوظائف المعروضة موجودة فعلًا أو معنونة Future concept؟
- هل تحترم الباقة والـfeature gating؟
- هل تم اختبار العربي RTL والإنجليزي LTR؟
- هل يوجد تصميم للحالات غير المثالية، وليس Happy path فقط؟
- هل CTA الأساسي واضح ويوجد CTA أساسي واحد في كل لحظة؟
- هل النصوص والأسعار والأسماء الطويلة تعمل بدون كسر التخطيط؟
- هل تجربة المنيو سريعة بإبهام واحد وبدون تسجيل حساب؟
- هل الـcontrast والـfocus والـtouch targets مناسبة؟
- هل يمكن بناء التصميم من مكونات قابلة لإعادة الاستخدام في Vue؟
- هل حافظ على Warm/Indigo/Tenant-branded contexts بدل خلطها؟
- هل يتجنب إضافة خدمات غير موجودة دون توضيح؟
